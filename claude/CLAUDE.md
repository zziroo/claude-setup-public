# General working rules (all projects)

- Reply to the user in Turkish; keep status messages short.
- Usage limits: sessions, subagents and scheduled tasks share the weekly limits. Check `get_usage` before a large fan-out.
- Memory and vault notes are snapshots. Verify live state (server, repo, version) before acting on or asserting them.
- Our rules, hooks, skills and agents are a thin layer over what Claude Code and the desktop app do natively; build on the native feature and add only what it lacks. Inventory with each piece's reason and its "delete when" condition: vault `20-Areas/working-rules/ozel-yapilar-envanteri.md`. When a native feature covers a piece, propose removing ours instead of running both; when adding a piece, add its row.
- Session title (desktop app): keep it current with `mcp__ccd_session_mgmt__set_session_title` (session_id "self"). Format `<proje>: <konu>`, Turkish, short. In the ZZ root (no project folder) the prefix is the topic, not "ZZ": `sistem:` (Claude Code, orkestra, kurulum, hesap/araç ayarları), `araştırma:` (dış repo ve fikir incelemeleri), `kişisel:`; work that belongs to a project takes that project's name as its prefix. Set it once the task is clear and update it whenever the topic shifts (no need to ask; it is one cheap call). Don't rename on every small step.
- Closing a session (desktop app): when everything the user asked for is done and nothing waits on them (no open decision, no pending commit/push/deploy question, no running agent or side session), end the turn with `wrap_up`, `ask` "Oturumu bitireyim mi?" and one reply button `Bitir`; this overrides wrap_up's bare recap for a turn with nothing pending. A pending decision goes first; the button comes on a later turn. Not on short answers, mid-work steps, in subagents or in worker sessions (a worker delivers instead; see Orchestration → two kinds of side session). Never close a session unasked. When the user answers `Bitir`, or says in any wording that they are closing (`kapatıyorum`, `kalmadıysa kapatayım`, `komple çıkalım`), run the `/bitir` flow: read `~/.claude/skills/bitir/SKILL.md` and follow it (the Skill tool can't start it, `disable-model-invocation` is on). A question such as `iş bitti mi?` gets an answer plus the button, not the flow. The same pattern hands a long session over: when the user answers `Yeni oturumda sürdür` (the hand-off offer from the context hook, see Orchestration → Coordinator) or asks to move to a new session, read `~/.claude/skills/devir/SKILL.md` and follow it: save to the vault, open the fresh session with a full brief and archive this one in one go, with no closing questions.

## Orchestration
- Sizable multi-step work: the main chat is the coordinator. It plans, asks the user for product decisions, delegates to background subagents (`run_in_background: true`), then reviews, tests and commits. Agents edit the working copy in place and don't commit; use `isolation: "worktree"` (own branch) only when parallel agents could touch overlapping files or the work is risky or experimental. This is a standing permission; don't ask per task.
- Side sessions (`start_session`, desktop app) vs subagents: a subagent stays the default for mechanical, review, discovery and single-slice work (cheapest, invisible to the user). Use a side session instead when (a) project work comes up in the ZZ root session: start it directly in the project's folder (`preset` or `cwd`, from `list_start_targets`) with the handoff note as the brief, instead of writing the note to the vault and waiting for the user to open a session; (b) the work will run for hours or the user will want to watch and steer it; (c) it is a self-contained next task better started fresh than from a long history. `context: "fork"` only while this conversation is short; otherwise `"fresh"` with a full brief. A proposal card (`own_initiative`) always opens in the current folder and cannot carry `preset`/`cwd`, so never propose project work from the ZZ root as a card: say in one line that it belongs in the project's session and start it with `user_asked` + `preset` once the user says go (learned: a project's backup session opened in the ZZ root instead of the project folder). Workflows and cloud sessions only when the user asks.
- Two kinds of side session, decided when it starts (both sides' steps are in `~/.claude/skills/teslim/SKILL.md`: read it before starting a worker or acting on its delivery). **Worker** (işçi oturum): a slice of this session's own task whose result comes back here; its brief ends with the line `Bu bir işçi oturum: işi teslim ederken ~/.claude/skills/teslim/SKILL.md dosyasını oku ve uygula.` A worker delivers (vault note + report) instead of asking "Oturumu bitireyim mi?", and does not archive itself unless the user themself closes it there. The coordinator reads the delivery note and reviews the work; merging stays with the project's rules and the user's word. It then archives the worker without asking (standing permission granted by this file, for the archive only) once the worker's branch, if it has one, is merged or the user dropped the work, and nothing in it waits on the user. **Independent** (bağımsız oturum): work whose result this session does not need (a "New session" offer, a follow-up card, project work handed off from the ZZ root); detach it as soon as it starts (`detach_session`) so it shows at top level, closes with its own `Bitir` and is not archived with this session. Unsure which kind: independent.
- Workflow scripts (measured on one project session: 12 runs, 112 agents, 87% of the session's cost): a script is written under the rules of this file, and the measured scripts carried them (explicit `model` and `effort` on every `agent()`, the lean-context text, `inceleme`/`supheci` as the review stage, a short return object), so no separate workflow rules. Sizing stays the script's job (at least a third of the measured agents passed 200k and 11 passed 100 calls): a build or fix stage expected to pass ~100 calls is split into stages with a handoff object. The `ajan-tavani` hook also reaches workflow agents, but there it only tells the agent to stop widening and to list what is left in its return (no later stage may exist to take a handoff), so it does not replace the split.
- Inline vs agent: an agent starts cold (~45–50k tokens of context). Go inline for short work with little reading (one-line fix, config or memory edit, git/deploy steps, quick check). Delegate when it needs a lot of reading or editing, even if the change is small, and whenever the coordinator's context is getting large.
- Split by feature (vertical slice), not by role. Parallel agents only on areas that don't overlap.
- Agent size: cost is context × calls, not agent count (each call re-reads the whole context), and very long contexts also lower quality. Cache reads are cheap, so a call at 400–500k costs only ~1.3x one under 200k and the jump comes past 500k (~3x); output, call count and the model's price drive the bill more than context size (measured over a month of sessions). The primary cap is ≤200k context per agent. Call count is a signal, not a hard stop: around 100 calls, split at the next natural phase boundary (a fresh agent with a short handoff note: files, decisions, hypotheses, what's left); a debugging agent close to the root cause may finish first rather than lose its hypotheses mid-investigation. Plan work that would take 150+ calls as phases from the start. Don't split small work; a cold start is cheap. The `ajan-tavani.mjs` PostToolUse hook reminds the agent itself at 200k context, every ~40 calls past 100, and every 5 screenshots; the coordinator no longer needs to repeat these caps in every brief, but a brief for work expected to exceed them still says where the phase boundary is.
- Repeated same-pattern work (e.g. several themes): one agent builds the first instance plus the shared seam and lists the files involved; the rest get that exact spec. Mechanical repeats may go to `sonnet`; design and feel stay on `opus`.
- Every agent prompt includes the lean-context rule: if the project has a code map (`docs/kod-haritasi.md` or wherever its CLAUDE.md points), read it first and search from there; read a file of up to ~500 lines whole in one call (cheaper than several slices, since every extra call re-reads the whole context, and the agent sees the full picture); read only line ranges of larger files, guided by the map or a grep; don't re-read files already read; pipe build/test/install output through `grep -iE "error|fail|warn"` first, then `tail -40`, never the full log. Browser checks, in agents **and in the coordinator alike**: prefer `read_page` / `get_page_text` / `javascript_tool` over screenshots; a screenshot only when layout itself is the question, at `scale: 0.5`, and at the end rather than after every step (each image stays in context and is re-read on every later call). A coordinator that needs more than a handful of browser steps delegates the whole browser pass to an agent instead of driving it itself (learned: one coordinator session took 135 screenshots and reached 628k context, 62 $ in a day).
- Discovery before code: when a task needs "find where X lives / which files touch Y", run that first as the `kesif` agent type (`~/.claude/agents/kesif.md`: Haiku, read-only, reads the code map first, returns file:line lists) or a few greps inline and put the resulting file:line list in the Opus agent's brief, so the Opus agent starts editing instead of searching.
- Code map: every project with real code gets `docs/kod-haritasi.md` via the global `kod-haritasi` skill (template, rules, and `~/.claude/skills/kod-haritasi/harita.mjs iskelet|kontrol`). Before a commit that adds, deletes or moves files or changes an area's entry point, the coordinator runs `harita.mjs kontrol` and fixes the map in the same commit. A project without a map: offer to create one when starting sizable work there.
- Coordinator: rely on the review agent's findings instead of reading whole agent diffs; past ~400k context, offer a hand-off to a fresh session, as a suggestion and never mid-flow: at the next natural point (a step or phase done, a commit made, a question for the user) `wrap_up` asks "Yeni oturumda sürdüreyim mi?" with buttons `Yeni oturumda sürdür` and `Burada devam`; mid-debugging or with live hypotheses, finish that point first, because a hand-off there costs quality. After `Burada devam`, don't offer again until the context grows by ~50k. The `baglam-uyarisi.mjs` UserPromptSubmit hook injects this above 400k (no separate warning line to the user) and a reminder when an old session is reopened above 150k (then tell the user in one line). 400k is where a hand-off pays for its cold start (~2 $); at 300k it cost ~60 $/month more than staying. `autoCompactWindow` 500000 in `settings.json` is only a safety net for forgotten sessions; after a compaction the `sikistirma-sonrasi.mjs` SessionStart hook points back to the raw transcript, and vault notes are written from that, not from the summary. Check `get_usage` context when a session passes ~2 hours or ~100 calls. Don't resume an old session whose context is already above ~150k for new work; start a fresh session with a short brief (measured: week-old sessions reopened above that cost 7–11 $ for a few dozen calls).
- Agents never commit to main, merge, tag, release, deploy, touch secrets or SSH into production (scheduled read-only routines may read production over SSH). The coordinator does those within the project's rules.
- Models: the user picks the coordinator's model and effort per session; subagents never inherit it. Default `model: "opus"` with `effort: "medium"` (raise to `"high"` for cross-cutting or design-heavy work and deep reviews); `sonnet` for narrow well-specified changes, verifier/skeptic passes and tooling; `haiku` (`kesif`) or Explore for read-only search, file discovery, log/test-output summaries and pre-publish reads of internal text; outward-facing text (store listings, brand copy, public pages) gets `sonnet`. Always pass `model` explicitly.
- Advisor, when the advisor tool is enabled (measured: 350 calls in six days, ~666 $ at list price, ~12 h of waiting, a median 2 min per call; the real catches came from the call before declaring done, the call before starting mostly just confirmed the plan). This overrides the advisor tool's own "call before substantive work" guidance, in the coordinator, in subagents and in workflow agents alike: call `advisor` at most once per task, before declaring done, and only when the task wrote code or produced a decision, measurement or report someone will act on; one more call is fine when genuinely stuck. Never before starting, never in a short task (under ~15 calls), never in a read-only agent (`inceleme`, `supheci`, `kesif`, Explore, jury, critique or design-reading stages). If the catches are not worth the wait, propose turning it off (`/advisor off`).
- Relay agent results concisely; never present unverified agent claims as verified. Clean up any worktrees and branches after merging.

## Review gate
- Agent types (`~/.claude/agents/`): `inceleme` (review, opus medium) and `supheci` (skeptic, sonnet) carry the read-only rules, scope and output format below; the brief only names the diff (base/target), the area, and whether it is a risky area (then pass `effort: "high"`).
- Before committing or merging agent code changes (a branch or the working-tree diff), a separate read-only review agent (`inceleme`, not the author) checks the diff for security and correctness bugs, with verified file:line findings. Tell review agents to stay read-only: `git diff` / `git show`, no checkout and no changes to the main working copy. Scope the review to the diff: the diff plus ~40 lines around each hunk and the direct callers of changed functions; no whole-file or whole-repo reads; aim for ≤30 tool calls and ≤120k context. Exception: diffs touching auth/sign-in, payments/IAP, server or API code, permissions, secrets handling or data migrations get `effort: "high"`, may follow callers beyond the direct ones, and have no call cap (still ≤200k context).
- Non-code work (memory, vault, docs, settings): no review agent. The coordinator re-reads the changed files and checks links and secrets itself, and never trusts the agent's report alone.
- Medium-or-higher findings: a skeptic agent (`supheci`, sonnet) tries to refute each against the code (CONFIRMED / REFUTED / DOWNGRADE) and judges the proposed fix. The coordinator decides and reports disagreements. No findings, no skeptic.
- Fix high and critical findings before merging.

## Decision split
- The user decides: what to build and its priorities; releases, deploys and irreversible or outward-facing actions; budget, security boundaries and product feel.
- Claude decides how (agent split, models, testing, code structure) and briefly reports what it chose.

## Secrets and production
- Secrets in tool output: never read a terminal tab while a command that prints a secret runs, never `read_page` a panel settings screen (use `find`), and dump only key names from secret files with a delimiter-independent mask (`awk '{sub(/[=[:space:]].*/,""); print}'`; `cut -d= -f1` misses tab-separated lines).
- Reach servers through `~/.ssh/config` aliases; never spell out keys, `-i`/`-o` flags or IPs. Put an ssh/scp call alone in its own Bash call, not chained with local commands (`cd … && ssh …`): a compound command must match a permission rule in every part, otherwise the auto-mode classifier blocks it.
- The auto-mode classifier refuses production deploys, `authorized_keys` writes and scheduled-task deletion even under a general "fix everything" request: don't work around it; put the steps in one script for the user's terminal, or ask for explicit approval of that action.

## Tools
- Orchestration report: `~/.claude/orchestration-report/`, run `node report.mjs [--session <id>] [--project <dir-key>]` (writes HTML and JSON to `out/`). Publish as an Artifact only when asked, after reading the whole HTML. Details and quirks: vault `20-Areas/working-rules/araclar-ve-raporlar.md`.

## Second brain
- Obsidian vault (Markdown) at `~/ZZ/brain`: project decisions, lessons, runbooks, session summaries. Never read it wholesale: `Home.md`, then the project's `_overview.md`, then grep for specific notes.
- After a substantial session, or when asked, write decisions (with why + rejected alternatives) and lessons there, following `~/ZZ/brain/CLAUDE.md`. Never write secrets into it.

## Compact Instructions
When this conversation is compacted, keep in the summary: every decision with its reason and the alternatives rejected; the user's product decisions and preferences in their own words; measured numbers and results; what was tried and failed; open questions and anything unverified; files, commits, branches, PRs and sessions touched (paths and ids); work still pending, with the exact next step; and which of these are not yet written to the vault. Drop tool output that is already reflected in files or commits.
